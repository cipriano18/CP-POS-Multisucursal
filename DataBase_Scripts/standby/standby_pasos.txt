# CP_POS — Oracle Database 21c Enterprise con Oracle Data Guard

## 1. Descripción del proyecto

Este proyecto implementa la base de datos **CP_POS** sobre Oracle Database 21c Enterprise, utilizando Oracle Data Guard para mantener una base de datos primaria y una base de datos física standby.

La arquitectura utiliza dos contenedores Docker:

- **dg-primaria:** base de datos primaria inicial.
- **dg-standby:** base de datos física standby.

La configuración permite mantener una copia sincronizada de la información, supervisar la replicación y realizar un failover automático mediante **Data Guard Broker y Fast-Start Failover (FSFO)**.

El contenedor anterior de Oracle XE se conserva detenido como respaldo. No se elimina ni se reutilizan directamente sus archivos físicos de datos.

## 2. Arquitectura utilizada

| Elemento | Configuración |
|---|---|
| Motor de base de datos | Oracle Database 21c Enterprise |
| Imagen Docker | `container-registry.oracle.com/database/enterprise:21.3.0.0` |
| Base de datos | `ORCLCDB` |
| PDB | `ORCLPDB1` |
| Nombre único primaria | `ORCLCDB` |
| Nombre único standby | `ORCLSTBY` |
| Contenedor primaria | `dg-primaria` |
| Contenedor standby | `dg-standby` |
| Puerto de primaria | `1541` |
| Puerto de standby | `1542` |
| Puerto interno Oracle | `1521` |
| Alias de conexión primaria | `primaria_dg` |
| Alias de conexión standby | `standby_dg` |

La base de datos primaria utiliza el servicio `ORCLPDB1` para las conexiones de la aplicación CP_POS.

Dentro del contenedor:


```sql
SELECT db_unique_name, database_role, log_mode
FROM v$database;

```

```sql
ALTER SESSION SET CONTAINER = ORCLPDB1;
```

### 6.4. Configurar FORCE LOGGING

```sql

```

### 6.5. Configurar el área de recuperación

Dentro del contenedor:

```bash
mkdir -p /opt/oracle/oradata/fra
```

En SQL*Plus:

```sql
ALTER SYSTEM SET db_recovery_file_dest_size = 10G SCOPE=BOTH;

ALTER SYSTEM SET db_recovery_file_dest = '/opt/oracle/oradata/fra' SCOPE=BOTH;
```

### 6.6. Configurar la administración de archivos standby

```sql
ALTER SYSTEM SET standby_file_management = AUTO SCOPE=BOTH;
```

```sql
ALTER SYSTEM SET dg_broker_config_file1 =
'/opt/oracle/oradata/ORCLCDB/dr1ORCLCDB.dat' SCOPE=BOTH;

ALTER SYSTEM SET dg_broker_config_file2 =
'/opt/oracle/oradata/ORCLCDB/dr2ORCLCDB.dat' SCOPE=BOTH;

ALTER SYSTEM SET dg_broker_start = TRUE SCOPE=BOTH;
```

### 6.8. Habilitar Flashback Database

```sql

```

### 6.9. Verificar los redo logs

## 8. Duplicación de la base de datos con RMAN

La base standby se crea a partir de la base primaria mediante una duplicación activa.

### 8.1. Conectarse a la primaria

Desde el contenedor standby:

```bash
sqlplus sys@PRIMARIA_DG as sysdba
```

### 8.2. Iniciar RMAN

Desde la terminal del contenedor:

```bash
rman TARGET sys@PRIMARIA_DG AUXILIARY sys@STANDBY_DG
```

### 8.3. Ejecutar la duplicación

Dentro de RMAN:

```rman
DUPLICATE TARGET DATABASE
FOR STANDBY
FROM ACTIVE DATABASE
DORECOVER
SPFILE
SET db_unique_name='ORCLSTBY'
SET fal_server='PRIMARIA_DG'
SET log_archive_dest_2=''
SET dg_broker_config_file1='/opt/oracle/oradata/ORCLCDB/dr1ORCLSTBY.dat'
SET dg_broker_config_file2='/opt/oracle/oradata/ORCLCDB/dr2ORCLSTBY.dat'
SET dg_broker_start='TRUE'
NOFILENAMECHECK;
```

Este proceso crea la base física standby utilizando la información de la primaria.

## 9. Configuración de Data Guard Broker con DGMGRL

### 9.1. ¿Qué es DGMGRL?

**DGMGRL** es la herramienta de línea de comandos de Oracle Data Guard Broker. Permite administrar la configuración de Data Guard, agregar bases de datos, habilitar la configuración, validar el standby y administrar Fast-Start Failover.

Los comandos de esta sección se ejecutan dentro de la consola DGMGRL, no directamente en PowerShell ni en SQL Developer.

### 9.2. Entrar al contenedor primario

Desde PowerShell:

```powershell
docker exec -it dg-primaria bash
```

### 9.3. Abrir DGMGRL

Dentro del contenedor:

```bash
dgmgrl
```

Conectarse a la primaria:

```text
CONNECT sys@primaria_dg;
```

### 9.4. Crear la configuración Broker

```text
CREATE CONFIGURATION cp_pos_dg AS
PRIMARY DATABASE IS ORCLCDB
CONNECT IDENTIFIER IS PRIMARIA_DG;
```

### 9.5. Agregar la base standby

```text
ADD DATABASE ORCLSTBY AS
CONNECT IDENTIFIER IS STANDBY_DG
MAINTAINED AS PHYSICAL;
```

### 9.6. Configurar los identificadores estáticos

Para la primaria:

```text
EDIT DATABASE ORCLCDB SET PROPERTY
StaticConnectIdentifier='(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=dg-primaria)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=ORCLCDB_DGMGRL)(SERVER=DEDICATED)))';
```

Para el standby:

```text
EDIT DATABASE ORCLSTBY SET PROPERTY
StaticConnectIdentifier='(DESCRIPTION=(ADDRESS=(PROTOCOL=TCP)(HOST=dg-standby)(PORT=1521))(CONNECT_DATA=(SERVICE_NAME=ORCLSTBY_DGMGRL)(SERVER=DEDICATED)))';
```

### 9.7. Habilitar la configuración

```text
ENABLE CONFIGURATION;
```

### 9.8. Verificar la configuración

```text
SHOW CONFIGURATION;

SHOW DATABASE ORCLSTBY;

VALIDATE DATABASE ORCLSTBY;
```

## 10. Configuración de Fast-Start Failover (FSFO)

Fast-Start Failover permite que Data Guard Broker realice un cambio automático de rol cuando detecta que la primaria no está disponible y se cumplen las condiciones configuradas.

### 10.1. Configurar los identificadores del Observer

Dentro de DGMGRL:

```text
EDIT DATABASE ORCLCDB SET PROPERTY
ObserverConnectIdentifier='primaria_dg';

EDIT DATABASE ORCLSTBY SET PROPERTY
ObserverConnectIdentifier='standby_dg';
```

### 10.2. Configurar los destinos de failover

```text
EDIT DATABASE ORCLCDB SET PROPERTY
FastStartFailoverTarget='ORCLSTBY';

EDIT DATABASE ORCLSTBY SET PROPERTY
FastStartFailoverTarget='ORCLCDB';
```

### 10.3. Configurar las propiedades de FSFO

```text
EDIT CONFIGURATION SET PROPERTY
FastStartFailoverThreshold=30;

EDIT CONFIGURATION SET PROPERTY
FastStartFailoverAutoReinstate=TRUE;

EDIT CONFIGURATION SET PROPERTY
FastStartFailoverPmyShutdown=TRUE;

EDIT CONFIGURATION SET PROPERTY
FastStartFailoverLagLimit=0;
```

### 10.4. Iniciar el Observer

El Observer se ejecuta dentro del contenedor standby.

Desde otra ventana de Windows PowerShell:

```powershell
docker exec -it dg-standby bash
```

Dentro del contenedor:

```bash
dgmgrl
```

Conectarse a la primaria:

```text
CONNECT sys@primaria_dg;
```

Iniciar el Observer:

```text
START OBSERVER;
```

En esta implementación el Observer se mantiene en primer plano dentro del contenedor standby. Si se cierra la sesión o se pierde ese contenedor, también se pierde el proceso Observer. Para una instalación productiva se recomienda ejecutarlo en un equipo independiente.

### 10.5. Habilitar Fast-Start Failover

En la consola DGMGRL:

```text
ENABLE FAST_START FAILOVER;
```

### 10.6. Verificar FSFO

```text
SHOW CONFIGURATION;

SHOW FAST_START FAILOVER;

SHOW OBSERVER;

SHOW DATABASE VERBOSE ORCLCDB;

SHOW DATABASE ORCLSTBY;
```

La configuración debe mostrar FSFO habilitado y el Observer activo.

## 14. Módulos adicionales del proyecto

Los módulos adicionales, como Padrón, Notificaciones y jobs, deben adaptarse a la nueva arquitectura.

Las referencias de conexión deben cambiar de:

- Contenedor anterior: `eif402-oracle21c-oficial`.
- Nueva primaria: `dg-primaria`.
- PDB anterior: `XEPDB1`.
- Nueva PDB: `ORCLPDB1`.

Consideraciones:

- El archivo utilizado por Padrón debe estar disponible en la primaria; la tabla correspondiente se replica, pero el archivo físico no.
- El wallet SMTP debe existir en ambos contenedores en `/opt/oracle/wallets/smtp`.
- Se debe volver a configurar `CORREO_ALERTAS_BD` y `CP_CONFIGURACION_CORREO`.
- Se debe generar una nueva clave de cifrado.
- Las claves de cifrado, las contraseñas y las claves de roles no se migran automáticamente.
- Se encuentra pendiente completar la especificación de `PKG_CP_NOTIFICACIONES` y el privilegio `GRANT EXECUTE ON DBMS_LOCK` para CP_POS.
- Los objetos que todavía aparezcan INVALID deben revisarse antes de considerar completa la instalación de estos módulos.

## 17. Prueba de lectura en la standby

Para verificar que la información de CP_POS está disponible en la standby, se puede realizar la prueba de lectura documentada.

El procedimiento consiste en detener temporalmente la aplicación de redo, abrir la base standby en modo de solo lectura, abrir la PDB y consultar la información de CP_POS. Después se devuelve a MOUNT y se habilita nuevamente la aplicación de redo.

Esta prueba debe realizarse teniendo en cuenta las condiciones de licencia de Oracle Active Data Guard. No debe confundirse la apertura temporal de solo lectura con el estado normal de aplicación de redo.

## 18. Prueba final de failover automático (FSFO)

Esta prueba demuestra el cambio de rol de la base de datos standby cuando la primaria deja de estar disponible.

### 18.1. Verificar el estado inicial de la primaria

En SQL Developer o PL/SQL Developer, conectado a la base primaria como SYS:

```sql
SELECT DATABASE_ROLE, OPEN_MODE
FROM V$DATABASE;
```

El estado inicial esperado es:

```text
PRIMARY
READ WRITE
```

### 18.2. Cambiar a la PDB

```sql
ALTER SESSION SET CONTAINER = ORCLPDB1;
```

### 18.3. Crear la tabla de prueba

```sql
CREATE TABLE FSFO_PRUEBA (
    ID NUMBER PRIMARY KEY,
    MENSAJE VARCHAR2(200),
    FECHA DATE DEFAULT SYSDATE
);
```

### 18.4. Insertar los registros antes del failover

```sql
INSERT INTO FSFO_PRUEBA (ID, MENSAJE)
VALUES (1, 'Registro antes del failover');

INSERT INTO FSFO_PRUEBA (ID, MENSAJE)
VALUES (2, 'Prueba de replicacion Data Guard');

INSERT INTO FSFO_PRUEBA (ID, MENSAJE)
VALUES (3, 'Verificacion de FSFO');

COMMIT;
```

### 18.5. Verificar la información

```sql
SELECT *
FROM FSFO_PRUEBA
ORDER BY ID;
```

Los tres registros deben estar guardados en la primaria y disponibles en la standby después de la replicación.

### 18.6. Verificar el estado de FSFO

Desde DGMGRL:

```text
SHOW CONFIGURATION;

SHOW FAST_START FAILOVER;

SHOW OBSERVER;
```

Se comprueba que FSFO esté habilitado y que el Observer esté activo.

### 18.7. Simular la caída de la primaria

Desde Windows PowerShell:

```powershell
docker kill dg-primaria
```

Este comando simula la caída del contenedor primario para comprobar el funcionamiento del failover.

### 18.8. Verificar el cambio de rol

Entrar al contenedor standby:

```powershell
docker exec -it dg-standby bash
```

Iniciar DGMGRL:

```bash
dgmgrl sys@standby_dg
```

Consultar:

```text
SHOW CONFIGURATION;
```

El resultado observado después de la caída mostró:

- `ORCLSTBY` como Primary database.
- `ORCLCDB` como Physical standby database que necesitaba reintegración.
- FSFO habilitado en modo Zero Data Loss.
- Estado de configuración WARNING mientras la antigua primaria se encontraba fuera de servicio.

### 18.9. Verificar el rol de la nueva primaria

Desde SQL Developer, conectado a ORCLSTBY:

```sql
SELECT DATABASE_ROLE, OPEN_MODE
FROM V$DATABASE;
```

El resultado comprobado fue:

```text
PRIMARY
READ WRITE
```

Cambiar a la PDB:

```sql
ALTER SESSION SET CONTAINER = ORCLPDB1;
```

Consultar los registros:

```sql
SELECT *
FROM FSFO_PRUEBA
ORDER BY ID;
```

Se verificó que los tres registros anteriores al failover estaban disponibles en la nueva primaria.

### 18.10. Insertar un registro después del failover

En la nueva primaria `ORCLSTBY`:

```sql
INSERT INTO FSFO_PRUEBA (ID, MENSAJE)
VALUES (4, 'Registro insertado despues del failover');

COMMIT;
```

Consultar nuevamente:

```sql
SELECT *
FROM FSFO_PRUEBA
ORDER BY ID;
```

El cuarto registro demuestra que la nueva primaria acepta operaciones de escritura después del failover.

```text
dg-primaria
```

### 19.2. Entrar al contenedor standby

Desde Windows PowerShell:

```powershell
docker exec -it dg-standby bash
```

### 19.3. Comprobar la configuración mediante DGMGRL

Desde el contenedor standby:

```bash
dgmgrl sys@standby_dg
```

Consultar el estado:

```text
SHOW CONFIGURATION;
```

- `ORCLSTBY` continúa como primaria.
